# Deployment and recovery review

Reviewed commit `8e45fe5`. Six isolated tests reproduced the following failures using temporary files, a filesystem replica, and fake service controllers. No real services or accounts were changed. Findings 2, 3, 5, and 6 are now fixed and have regression tests. Findings 1 and 4 remain open. The access-control fixes listed afterward are included in this change.

1. **P1: Generation allocation can reuse numbers already held by peers.** `allocateGeneration` checks peer history only when the local archive directory is empty. After restoring an older generation onto a rebuilt host, the newly recovered archive makes that directory nonempty. The next snapshot or accept can reuse an existing remote generation. A restricted receiver rejects the conflict; the legacy transport can report success while retaining the old remote manifest.

   Reproduction: retain local generation 1 and peer generation 10, then allocate the next generation. The result is 2. Fix: persist the highest observed generation when retrieving or recovering metadata, consult it for every allocation, and reconcile remote history before creating a new lineage after local state loss. Code: `cmd/warden/lineage.go:79`, `cmd/warden/retrieve.go`, `internal/replicate/replicate.go`.

2. **Fixed, P1: Failed rollback deletes the saved pre-restore copy.** Restore reports an incomplete rollback but its deferred cleanup still removes every staged previous file. The operator is told to recover manually after the data needed for that recovery has been discarded.

   Reproduction: restore a file, then have the validation hook replace its destination with a directory and return an error. Rollback cannot rename the saved file over that directory. The call reports failure and leaves no temporary file containing the original bytes. Fix: retain failed rollback artifacts, report their paths, and record transaction state for explicit recovery. Code: `internal/restore/restore.go:133`.

3. **Fixed, P1: A corrupt local archive blocks recovery from a valid peer.** Recovery finds and validates the peer's copy, then attempts to archive it locally. Immutable archive publication rejects the already existing corrupt file, so the live manifest is never recovered. `retrieve --apply` encounters the same conflict.

   Reproduction: remove the live manifest, corrupt local archive generation 1, and keep a valid generation 1 on a configured peer. `ensureManifest` fails with `invalid archive`. Fix: quarantine invalid local metadata under the operation lock, retain the damaged bytes for inspection, and publish the verified replacement. Valid but conflicting manifests must remain an explicit conflict. Code: `cmd/warden/recovery.go:266`, `internal/manifest/manifest.go`.

4. **P2: Repeating restore does not retry a failed service start.** The first restore can publish correct files and fail to start the service. The next restore plan sees unchanged hashes and modes, so Apply skips everything and never attempts to start the service. The watch reload queue does not record failures from explicit restore.

   Reproduction: make the controller's first Start return an error, replan against the now-restored file, and apply again. There is still only one start attempt. Fix: persist pending service transitions independently of file drift, including previous service state and whether rollback succeeded. Code: `internal/restore/restore.go:143`, `internal/restore/restore.go:286`, `cmd/warden/restore.go`.

5. **Fixed, P2: Backup verification can report healthy despite corrupt local metadata.** The verifier asks the recovery selector for one usable manifest per generation. A valid live manifest masks a corrupt local archive of the same generation, so the retained archive is never checked independently. That corrupt archive later blocks recovery as described above.

   Reproduction: keep a valid live generation and object but replace its archived JSON with invalid bytes. `checkBackups` returns `Healthy=true`. Fix: inspect the live pointer and each retained archive separately, then compare valid metadata across sources. Recovery selection should not substitute for a per-copy integrity check. Code: `cmd/warden/verifybackups.go:125`.

6. **Fixed, P2: Usable replica counts can include an unreadable tier.** When no usable manifest can be loaded for a selected generation, verification records a problem and skips the per-peer checks that mark replicas unusable. A peer with valid config objects but corrupt data metadata is still counted as a usable replica. The overall report is unhealthy, but the count is wrong.

   Reproduction: give a peer one valid config generation and one corrupt data generation. The report lists a data error and `UsableReplicas=1`. Fix: calculate completeness per source and tier, mark unresolved metadata as unknown or unusable, and count only sources that satisfy the full required set. Code: `cmd/warden/verifybackups.go:127`, `cmd/warden/verifybackups.go:234`.

## Access-control fixes

- **P1: The operator account could bypass the second-factor gate through sudo.** The installed and sentinel-generated rule allowed any arguments to the binary. A process running as that account could invoke commands such as `rotate-secret` directly as root. Both rules now permit the exact `opmenu` invocation only. Other sudo grants to that account remain outside this rule's control.
- **P1: TOTP replay protection was not atomic.** Parallel requests could both read the old counter and accept the same code. Empty or malformed state was also treated as unused. Counter consumption now holds a cross-process file lock and atomically persists the counter; malformed state fails closed. Contending requests may be rejected and need a fresh attempt. Regression tests cover concurrent consumption, replay rejection, and corrupt state preservation.
- **P2: Managed SSH keys were checked as substrings and repaired by appending.** A commented entry satisfied the check, and additional unrestricted keys survived repair. Installation also skipped restrictions if the same public key appeared anywhere in the file. The dedicated key file is now checked against the exact managed entry and replaced on repair. This intentionally removes other keys from that dedicated account. Regression tests cover comments, additional entries, and removal of unapproved keys.
- **Access availability:** Fresh operator accounts now use `/bin/sh`, with root-owned directories and readable public-key files. Sudo preserves the two SSH variables the handler needs, and the managed key disables user startup scripts. Previously `nologin` blocked forced-command execution and default sudo environment filtering could discard the requested command. Existing accounts need the migration steps in DEPLOYMENT.md. OpenSSH documents command execution through the account's login shell and the original-command environment variable in its [sshd manual](https://man.openbsd.org/sshd.8).

These changes protect the intended operator entry point. They cannot exclude an attacker who already controls root on the host: root can read local secrets, change authentication code, and invoke local CLI operations. A blue-team-only authorization boundary that survives host compromise needs keys and authorization decisions on a trusted external machine. The deployment diagram and DESIGN.md now state that boundary.

Remaining security work: add effective SSH/sudo policy checks before deployment, test installation on the scored Linux image, enforce receiving quotas per source, and support off-host signing or approval. Receiving keys can currently read their assigned backups and fill their assigned storage; use filesystem quotas and separate source accounts. Optional manifest signatures do not prevent a compromised signer from signing new data.

## Deployment correction

The main installer writes its binary as root-owned mode 0700. The receiving account cannot execute that binary through its forced SSH command. Making it world-readable would expose the host credentials compiled into it. DEPLOYMENT.md now instructs operators to build a separate receiver without credential linker flags and install that binary as root-owned mode 0755. The deployment diagram shows the separate executable and per-source storage roots. This correction was based on the install script and receiver command; a fresh Linux installation was not performed.

## Validation

`go test -race -count=1 ./...`, `go vet ./...`, the Linux amd64 build, `bash -n deploy/install.sh`, and `git diff --check` passed. The installer test executes the access configuration functions in a temporary directory, mocks account creation and ownership changes, validates sudoers with `visudo`, and checks the generated key policy, modes, and account shell. It does not establish a real operator login or test Linux PAM policy. Markdown fences and Mermaid structure were checked; the diagram was not rendered during this review.

## Recovery refinements

Failed rollbacks now retain the pre-restore artifact and include its path in the error and the structured restore result. Services stay stopped after an incomplete rollback. This is not yet a durable transaction journal or a resume command.

Manifest recovery, retrieval, and `verify-backups --repair` can replace invalid regular-file archives after moving them to uniquely named `corrupt-manifest-<generation>-*.json` files. Valid conflicting generations and symlinks are refused. The damaged bytes remain available for inspection.

Verification now reports a `manifests` matrix by tier, generation, and source alongside its object results. It reads live and archived metadata independently and checks peer metadata even when no usable manifest can be selected. A missing active baseline is reported without adopting an archive. Repairs report separate object and manifest counts plus quarantine paths.

A further availability bug was found during this pass: reading a manifest replaced with a FIFO could block a command indefinitely. Manifest loading and recovery now use the nonblocking regular-file reader, and verification has a FIFO regression test.

Regression tests cover failed rollback retention, automatic and explicit recovery past corrupt archives, valid conflicts, symlinks, read-only verification, metadata repair, missing active baselines, and unusable peer tiers. All tests use temporary storage and fake service controllers.

The next workflow priorities are persistent generation history (finding 1) and retryable service transitions (finding 4). An account-maintenance preflight that runs before consuming a second factor would also save time when existing drift or a busy operation prevents an edit. The attribution review remains separate; these changes do not strengthen writer identification.
